# AI-обработка входящей заявки на перевозку

Прототип для тестового задания. Система читает входящую заявку в произвольном виде
(сообщение, письмо, Word, PDF, Excel), извлекает поля для заведения сделки и —
там, где данных не хватает или они допускают несколько прочтений — **не додумывает,
а формирует вопросы пользователю**.

---

## Запуск

```bash
pip install -r requirements.txt
```

```bash
copy .env.example .env
```

Впишите в `.env` ключ `DEEPSEEK_API_KEY` и запустите:

```bash
python -m uvicorn app.main:app --reload
```

Интерфейс — <http://127.0.0.1:8000>, автодокументация API — <http://127.0.0.1:8000/docs>.

Без ключа приложение тоже работает: разбор переключается на детерминированный
экстрактор, и в интерфейсе честно написано «извлечено правилами».

Демо-заявки уже лежат в `samples/`. Пересобрать их (например, после правки
`make_samples.py`) можно так:

```bash
python samples/make_samples.py
```

Тесты (полностью офлайн, сеть не нужна):

```bash
python -m pytest -q
```

## Что происходит с заявкой

```
файл / текст
     │
     ├─ ingest ──────────► plain text + метаданные (txt, eml, docx, pdf, xlsx)
     │
     ├─ извлечение ──────► LLM (DeepSeek) → JSON с цитатами
     │                     └─ резерв: экстрактор на правилах
     │
     ├─ нормализация ────► справочники станций (ЕСР) и грузов (ЕТСНГ)
     │
     ├─ проверки ────────► детерминированные, независимые от модели
     │
     └─ вопросы ─────────► шаблоны + варианты ответа из справочника
```

Ключевое архитектурное решение: **модель отвечает только на вопрос «что написано
в заявке». Решение «можно ли с этим заводить сделку» принимает код.** Промпт
можно уговорить, проверку цитатой — нет.

---

## Как система не даёт себе выдумать данные

Пять независимых барьеров. Первый — самый важный.

**1. Цитата обязана найтись в исходном документе.** Промпт требует для каждого
непустого поля `evidence` — дословную цитату из заявки. После ответа модели
`app/validate/rules.py` ищет эту цитату в исходном тексте. Не нашлась — поле
понижается до «неоднозначно» и уходит в вопросы, а не в сделку. Модель не может
подделать цитату из текста, которого не видела.

**2. Числа проверяются отдельно.** Если модель вернула «40 вагонов», а в заявке
числа 40 нет, значение стирается. Это ловит попытку пересчитать тонны в вагоны.

**3. Однозначность определяется справочником, а не «на глаз».** «Москва» — это
6 грузовых станций, значит поле неоднозначно, и в вопрос уходит список станций
с кодами ЕСР. «Металл» — это лом, прокат, чугун, трубы или ферросплавы с разными
кодами ЕТСНГ и разным родом вагона, значит нужно уточнение.

**4. Кросс-проверки.** Станция отправления совпала с назначением; конец периода
раньше начала; период в прошлом; 25 вагонов и 100 000 тонн одновременно
(при типовой загрузке 69 т/ваг это расхождение в 60 раз); ставка без базы расчёта
или без НДС.

**5. Пустой документ — не пустая заявка.** PDF без текстового слоя не отправляется
в модель вообще: система сообщает, что нужен OCR или исходник. Модели не дают
шанса нафантазировать поля из ничего.

Отдельно: `null` в ответе модели — нормальный и ожидаемый результат. В промпте
это сказано прямо и подкреплено few-shot примером, где половина полей пустая.

## Демо-заявки и ожидаемое поведение

Кнопки в интерфейсе идут по нарастанию сложности.

| Заявка | Что должно получиться |
|---|---|
| `01_full.txt` | Все поля распознаны, коды ЕСР и ЕТСНГ проставлены, **вопросов нет**, «можно заводить сделку» |
| `02_incomplete.txt` | Станции и груз в порядке, **нет объёма и периода** → два блокирующих вопроса |
| `03_ambiguous.txt` | «из Москвы» → 6 станций на выбор; «металл» → 5 позиций ЕТСНГ; «15-20 вагонов в месяц» → объём не определён; «1500 за тонну» → нет НДС и валюты |
| `04_letter.eml` | Разбирается шапка письма, тело и цитата предыдущего письма; заявка полная |
| `05_zayavka.docx` | Заявка таблицей «поле / значение» — таблица разворачивается в текст |
| `06_plan.xlsx` | Помесячный план отгрузок; две строки на разные месяцы → вопрос о периоде |
| `07_scan.pdf` | **Нет текстового слоя** → одно сообщение «пришлите текстом», ни одного выдуманного поля |

Проверить барьер против выдумок вручную быстрее всего так: откройте
`03_ambiguous.txt` и посмотрите на станцию назначения. В тексте написано
«в порт на Дальнем Востоке» — система оставляет поле пустым и спрашивает,
хотя «угадать» Находку или Ванино было бы легко.

## API

| Метод | Ручка | Назначение |
|---|---|---|
| `POST` | `/api/parse` | JSON `{"text": "…"}` **или** multipart с файлом → результат разбора |
| `POST` | `/api/parse-sample` | `{"name": "03_ambiguous.txt"}` — разбор демо-заявки |
| `POST` | `/api/answer` | `{result, answers}` — ответы менеджера, пересчёт без обращения к модели |
| `GET` | `/api/samples` | список демо-заявок |
| `GET` | `/healthz` | статус, виден ли ключ, какая модель |

```bash
curl -F "file=@samples/05_zayavka.docx" http://127.0.0.1:8000/api/parse
```

### Структура ответа

Поле — не голое значение, а значение со статусом и доказательством:

```json
{
  "draft": {
    "station_from": {
      "value": "Москва",
      "raw": "Москва",
      "code": null,
      "evidence": "из Москвы",
      "status": "ambiguous",
      "confidence": 0.4,
      "comment": "Указан город «Москва», а не станция: в справочнике 6 станций этого узла",
      "candidates": [
        {"value": "Москва-Товарная-Павелецкая", "code": "191500", "hint": "МСК, Москва", "score": 1.0}
      ],
      "display": "Москва"
    }
  },
  "questions": [
    {
      "field": "station_from",
      "text": "Уточните станцию отправления…",
      "options": ["Москва-Товарная-Павелецкая (код 191500, МСК, Москва)", "…"],
      "priority": 10,
      "blocking": true,
      "reason": "ambiguous"
    }
  ],
  "ready_for_deal": false,
  "extractor": "llm",
  "warnings": [],
  "letter": "Здравствуйте!\n\nСпасибо за заявку…"
}
```

Статусы поля: `ok` (готово к сделке), `missing` (данных в заявке нет),
`ambiguous` (данные есть, но требуют уточнения), `low_confidence` (извлечено,
но не подтверждено проверками).

Обязательные поля — компания, обе станции, груз, объём, период: пока по ним есть
вопросы, `ready_for_deal = false`. Условия погрузки/выгрузки и бюджет
необязательны — их отсутствие вопросов не порождает, но если они присутствуют
и неоднозначны, уточнение всё равно формируется.

## Структура кода

```
app/
├─ ingest/          приведение форматов к тексту (text, eml, docx, pdf, xlsx)
├─ llm/             промпты, клиент DeepSeek, схема ответа модели, извлечение
├─ rules/           экстрактор на регулярках — резерв и перекрёстная проверка
├─ directory/       справочники станций и грузов + нормализация с fuzzy-поиском
├─ validate/        проверки (rules.py) и генерация вопросов (questions.py)
├─ pipeline.py      оркестрация всех шагов
├─ answers.py       применение ответов менеджера и пересчёт
├─ models.py        Pydantic-модели результата
└─ main.py          FastAPI: REST + страница
samples/            демо-заявки + генератор бинарных форматов
tests/              44 теста, все офлайн
```

## Особенности DeepSeek, учтённые в коде

Проверено на живом API перед реализацией:

* **Строгий `response_format: json_schema` недоступен** (`"This response_format
  type is unavailable now"`), работает только `json_object`. Поэтому схема живёт
  в промпте, а гарантию даёт валидация Pydantic на нашей стороне плюс один
  repair-заход: модели возвращают её же ответ вместе с текстом ошибки валидации.
* **`deepseek-v4-*` — reasoning-модели.** Основной бюджет токенов уходит в
  `reasoning_content`: на неоднозначной заявке замерено ~4 300 токенов у `pro`
  и до ~10 500 у `flash`. При `max_tokens=4000` ответ обрывается до JSON —
  отсюда значение по умолчанию 16 000.
* **Скорость.** `deepseek-v4-pro` отвечает за ~55–75 с на заявку. Параметр
  `LLM_REASONING_EFFORT=minimal` сокращает размышления и ускоряет ответ примерно
  в полтора раза — удобно для демонстрации.
* Валидаторы в `app/llm/schema.py` намеренно снисходительные: модель периодически
  отдаёт строку вместо объекта, число строкой или дату в формате `10.10.2026`.
  Ронять на этом весь разбор незачем.

## Что осознанно не сделано

Это прототип, а не production-система. За рамками осталось:

* **Справочники — демонстрационный срез.** ~115 станций и ~42 позиции ЕТСНГ.
  Названия станций, дорог, родов вагонов и типовые загрузки реальные, **коды ЕСР
  и ЕТСНГ — условные значения нужного формата**; об этом сказано в `_meta` внутри
  обоих JSON. В production слой `app/directory/` подменяется на реальную НСИ
  (АС ЭТРАН), интерфейс `lookup_station` / `lookup_cargo` при этом не меняется.
* **Нет хранилища.** Всё живёт в рамках запроса, история заявок не ведётся.
* **Нет аутентификации, очередей и воркеров.** Долгий вызов модели выполняется
  синхронно в threadpool; для потока заявок нужна очередь.
* **Нет интеграции с CRM.** `ready_for_deal` — это сигнал, а не вызов API сделки.
* **Нет OCR.** Скан распознаётся как скан, но не читается. Задел есть:
  у DeepSeek доступна `deepseek-v4-flash-vision-exp`.
* **Одна заявка = один маршрут.** Заявка на несколько направлений сразу будет
  помечена как неоднозначная, но не разложена на отдельные сделки.
* **Лемматизация — эвристика.** В резервном экстракторе падежи обрабатываются
  сравнением основ, без морфологического словаря. Порог настроен на точность:
  пропустить поле лучше, чем подставить чужое значение (у LLM-пути этой
  проблемы нет).

## Вопросы, которые стоит задать заказчику

Возникли по ходу работы — они меняют модель данных, а не только реализацию:

1. **Куда именно уходят поля?** Если целевая система — ЭТРАН или CRM с
   собственным справочником, нормализацию надо делать сразу в её коды, а не в ЕСР.
2. **Нужен ли род подвижного состава и признак собственности вагонов?**
   Для ставки это обычно важнее условий погрузки, но в списке полей его нет.
3. **Как считать объём при регулярных отгрузках?** «15 вагонов в месяц в течение
   года» — это одна сделка на 180 вагонов или 12 сделок? Сейчас система просит
   уточнить общий объём.
4. **Что делать с заявкой на несколько маршрутов в одном письме** — разбивать
   на сделки автоматически или отдавать менеджеру списком?
5. **Кто адресат вопросов** — клиент (тогда нужен готовый текст письма, он есть
   в поле `letter`) или менеджер (тогда достаточно списка в интерфейсе)?
6. **Ставка: с НДС или без по умолчанию?** Сейчас отсутствие признака считается
   поводом для уточнения; если в компании есть соглашение по умолчанию, вопрос
   можно снять.

# AI-обработка входящей заявки на перевозку

**Демо:** http://45.144.64.52:8000 · **Код:** https://github.com/tu66150nf1r3/zayavki-ai

---

## Что делает

Принимает заявку в том виде, в каком она реально приходит: текст сообщения, письмо
`.eml`, Word, PDF, Excel. Читает её и собирает карточку сделки — компания, станция
отправления, станция назначения, груз, объём и количество вагонов, период перевозки,
условия погрузки и выгрузки, ставка.

Главное — что система делает с неполными данными: **не достраивает их до
правдоподобных.** Каждое поле получает статус «распознано» / «нет данных» /
«неоднозначно», а по всем пробелам формируется список вопросов клиенту — с вариантами
ответа там, где их можно предложить, и готовым текстом письма. Пока остаются
блокирующие вопросы, заявка помечена как «сделку заводить рано».

Пример из демо. В заявке написано: «нужно возить металл из Москвы в порт на Дальнем
Востоке, примерно 15–20 вагонов в месяц, начать в ближайшее время». Система не выбирает
станцию за клиента, а отвечает:

* «Москва» — это 6 грузовых станций, вот список с кодами ЕСР;
* «металл» — это 5 позиций ЕТСНГ с разным родом вагона и тарифом;
* порт не назван — какой именно;
* объём вилкой и помесячно — общий объём перевозки неизвестен;
* период не назван, только «в ближайшее время».

Менеджер отвечает прямо в интерфейсе, заявка пересчитывается, и карточка доходит до
состояния «можно заводить сделку».

| Качество | 45 тестов, все офлайн — доступ к API для них не нужен |

## Как работает

Конвейер из четырёх независимых слоёв:

```
файл / текст → ingest → извлечение (LLM) → нормализация по справочникам → проверки → вопросы
```

Ключевое архитектурное решение: **модель отвечает только на вопрос «что написано
в заявке». Решение «можно ли с этим заводить сделку» принимает детерминированный код.**

Причина простая: промпт можно уговорить, проверку — нет. Поэтому после модели идут
барьеры, которые от неё не зависят:

1. **Цитата.** Модель обязана вернуть для каждого поля дословную цитату из заявки.
   Система ищет её в исходном тексте. Не нашлась — поле не попадает в сделку, а уходит
   в вопросы. Подделать цитату из текста, которого не было, модель не может.
2. **Числа.** Значение сверяется с текстом заявки — это ловит попытку пересчитать
   тонны в вагоны и выдать результат за исходные данные.
3. **Справочник.** Однозначность станции и груза определяется по справочнику, а не
   «на глаз»: один кандидат — в сделку с кодом, несколько или ни одного — вопрос.
4. **Кросс-проверки.** Маршрут из станции в неё же, период задом наперёд, 25 вагонов
   и 100 000 тонн одновременно, ставка без базы расчёта и без НДС.
5. **Нечитаемый документ.** PDF без текстового слоя вообще не отправляется в модель:
   система просит прислать исходник, а не фантазирует поля из пустоты.

Полезный побочный эффект такого разделения: если API недоступен, прототип продолжает
работать на детерминированном экстракторе и честно показывает в интерфейсе, чем именно
была разобрана заявка — моделью или правилами.

## Границы прототипа

Осознанно не делалось: справочники демонстрационные (названия реальные, коды условные),
нет хранилища заявок, аутентификации и интеграции с CRM, скан распознаётся как скан,
но не читается — OCR не подключался. Полный список ограничений и вопросов, которые
стоит обсудить по постановке, — в README проекта.
